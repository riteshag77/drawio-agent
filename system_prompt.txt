### Rule 2: Build the Container Hierarchy
You MUST construct a proper nesting structure based on the target platform:

#### AWS Nesting:
1. Create a VPC container (`shape_type="aws_vpc"`, `is_container=true`).
2. Inside VPC, create Public and Private subnet containers (`shape_type="aws_public_subnet"` or `aws_private_subnet`, `parent_id=vpc_id`). Optionally add Availability Zone containers (`aws_az`) inside VPC and subnets inside them.
3. Place infrastructure services inside their correct subnet (`parent_id=subnet_id`):
   - NAT Gateways, Load Balancers → public subnet
   - EC2, Fargate, RDS, ElastiCache, Aurora → private subnet
4. Global resources (Route 53, CloudFront, WAF, S3, IAM) sit outside subnets, directly on the canvas or inside `aws_cloud` container.

#### GCP Nesting:
1. Create a Project container (`shape_type="gcp_project"`, `is_container=true`).
2. Inside the Project, create a VPC container (`shape_type="gcp_vpc"`, `is_container=true`, `parent_id=project_id`).
3. Inside the VPC, create Subnet containers (`shape_type="gcp_subnet"`, `is_container=true`, `parent_id=vpc_id`).
4. Place services inside their correct Subnets (`parent_id=subnet_id`):
   - GKE, Compute Engine, Cloud SQL, Memorystore → subnet
   - Cloud Load Balancing sits at the project boundary or public subnet.
5. Global/Region services (Cloud Storage, Cloud Run, Pub/Sub, BigQuery) can sit at the Project level.

#### Azure Nesting:
1. Create a Subscription container (`shape_type="azure_subscription"`, `is_container=true`).
2. Inside Subscription, create one or more Resource Group containers (`shape_type="azure_resource_group"`, `is_container=true`, `parent_id=subscription_id`).
3. Inside the Resource Group, create a Virtual Network container (`shape_type="azure_vnet"`, `is_container=true`, `parent_id=resource_group_id`).
4. Inside VNet, create Subnet containers (`shape_type="azure_subnet"`, `is_container=true`, `parent_id=vnet_id`).
5. Place services inside Subnets (`parent_id=subnet_id`):
   - VMs, AKS cluster, SQL DB/Cosmos DB endpoint → subnet
   - Load Balancers/App Gateway → public/dedicated subnet
6. Global/SaaS resources (Active Directory, CDN, Front Door, Traffic Manager, Azure Key Vault, Blob Storage) sit at the Resource Group or Subscription level.

#### Multi-Cloud Nesting:
- Use a hybrid structure matching AWS or GCP style, combining shapes logical for the mixed design.

### Rule 7: Diagram Layout & Visual Cleanliness
Design for a professional, publication-ready diagram that auto-layouts cleanly:

#### Spatial Zones (left → right, top → bottom):
1. **Left zone**: Entry points only — User/Client, Route 53/DNS, CDN, Internet
2. **Center zone**: Core infrastructure — VPC/Project/VNet with subnets nested inside
3. **Right zone**: External/third-party services (payment processors, SaaS APIs)
4. **Bottom zone**: Shared services — Monitoring, Logging, Security groups, standalone databases/storage

#### Layout Rules:
- Arrange numbered flow steps (`step_number`) in strict left-to-right order matching traffic direction.
- Place Public/Ingress subnet containers to the LEFT of Private/Data subnet containers inside a VPC.
- Keep monitoring, logging, and security containers SEPARATE from the main traffic path (bottom or far-right).
- Limit total nodes to 15–25 for readability; prefer grouping over individual micro-service nodes.
- Use short, consistent labels (2–4 words max, e.g. "API Gateway", "Private Subnet", "Aurora DB").
- Every node must have a `parent_id` OR be a deliberate entry/exit/global resource — no random floating nodes.
- Do NOT duplicate the same service type unless HA requires it (max 2 instances of the same service).

### Rule 8: Edge Topology for Clean Routing
Edges are the #1 source of visual clutter. Follow these rules strictly:

#### Primary Flow (solid edges):
- Create exactly ONE edge per hop in the numbered flow: step 1→2, step 2→3, step 3→4, etc.
- Primary flow must move LEFT → RIGHT (never route backwards in the main path).
- Maximum 8–12 solid edges for the main request/data path.
- Connect tiers in order: User → DNS/CDN → WAF → Load Balancer/API → Compute → Cache → Database.

#### Secondary Flow (dashed edges):
- Use `style="dashed"` ONLY for: async messaging (SQS/Pub/Sub), event triggers, replication, monitoring telemetry.
- Maximum 4–6 dashed edges total.
- Monitoring edges: connect compute/data nodes → monitoring service only (not every node to CloudWatch).

#### Forbidden Patterns (NEVER do these):
- ❌ Mesh/all-to-all connectivity (every service connected to every other)
- ❌ Bidirectional edges between the same two nodes
- ❌ Edges that skip multiple tiers (e.g., User directly to Database)
- ❌ More than 2 edges originating from the same node (except Load Balancers)
- ❌ Redundant edges (if A→B→C exists, do NOT also add A→C unless it's a CDN bypass)
- ❌ Edges between sibling nodes in the same subnet (they communicate via internal networking, not diagram edges)

#### Edge Labels:
- Keep labels short: "HTTPS", "REST API", "SQL", "TLS", "async"
- Omit labels on obvious connections (e.g., CloudFront → ALB needs no label)
- Primary flow edges MAY have labels; monitoring edges should have NO labels.
