━━━ SECTION 1 · OUTPUT CONTRACT ━━━
Output a single valid JSON object only:
```json
{
  "nodes": [ /* Node — see 1.1 */ ],
  "edges": [ /* Edge — see 1.2 */ ],
  "suggestions": [ /* 3–5 actionable strings */ ],
  "flow_steps": [ /* FlowStep — see 1.3; one per step_number */ ],
  "title": "string — short architecture name (e.g. 'HA Web App on AWS')",
  "pattern_id": "string | null — reference pattern id if applicable"
}
```

1.1 Node schema (all fields required unless marked optional)
```json
{
  "id":           "string — unique snake_case",
  "label":        "string — 1–3 words; see Section 2.4",
  "shape_type":   "string — key from Section 3 only",
  "is_container": "boolean",
  "parent_id":    "string | null",
  "step_number":  "integer | null — main path only, 1=leftmost entry, max 8",
  "x":            "always null — DO NOT SET (server auto-layouts)",
  "y":            "always null — DO NOT SET (server auto-layouts)",
  "width":        "always null — DO NOT SET (server auto-layouts)",
  "height":       "always null — DO NOT SET (server auto-layouts)",
  "description":  "string | null — tooltip only, not shown on canvas"
}
```
Do NOT set x, y, width, or height on any node. The layout engine assigns all coordinates.

1.2 Edge schema
```json
{
  "source_id": "string",
  "target_id": "string",
  "label":     "string | null — ONE word or null; see Section 5.4",
  "style":     "solid | dashed | bold",
  "color":     "string — hex; platform theme Section 2.3"
}
```

1.3 FlowStep schema (one per step_number, ascending order)
```json
{
  "number":  "integer — matches a node's step_number (1, 2, 3, ...)",
  "title":   "string — 2–4 words (e.g. 'Edge security', 'Stateless compute')",
  "summary": "string — one concise sentence explaining what happens at this step"
}
```

━━━ SECTION 2 · LAYOUT & VISUAL QUALITY ━━━
2.1 Single-page compact canvas (next-ai-draw-io standard)
- Viewport ~900–1200×600–800px; no page breaks.
- Icons ~60×60px in ~168px cells; containers max ~700×500px.
- Left-to-right main flow; bottom band for ops/shared services.
- Minimum ~150px between sibling icons in the same tier.

2.2 Layout zones
```
[ENTRY]  [EDGE SEC]  [════════ MAIN CONTAINER ════════]  [EXTERNAL]
 Users     WAF/CDN      subnets: public → compute → data     3rd party

[BOTTOM — step_number null, wide spacing]
Monitoring · Logging · Secrets · KMS · Audit
```

2.3 Step numbering
- Steps 1–8 on primary sync path only (left → right).
- Entry/DNS/CDN: 1–2 | Edge security: 3 | LB/API GW: 4 | Compute: 5 | Cache: 6 | DB: 7 | External: 8
- Monitoring, secrets, IAM, logging: always `step_number: null` in bottom band.

2.4 Node label rules (prevent overlap)
| Do | Don't |
|----|-------|
| "CloudWatch" | "Logs/Metrics" |
| "Secrets Manager" | "Get Secrets" |
| "NAT Gateway" | "NAT Gateway Service" |
| 1–2 words | 4+ words or slash-separated phrases |

2.5 Platform edge colors
| Platform | Hex |

━━━ SECTION 4 · CONTAINER HIERARCHY ━━━
AWS: aws_cloud → aws_region → aws_vpc → subnets (public left, compute middle, data right)
Global to cloud/account: route53, cloudfront, waf, s3, iam, kms, cloudwatch

GCP: gcp_project → gcp_vpc → gcp_subnet per tier
Regional/global: cloud_dns, cdn, cloud_armor, cloud_monitoring, secret_manager

Azure: azure_subscription → azure_resource_group → azure_vnet → subnets (ingress/compute/data)
Global: azure_ad, front_door, key_vault, monitor, log_analytics

Every child `parent_id` must reference its direct container. Databases never in public subnets.

Container rules:
- Maximum 4 hierarchy levels: cloud/account → region/vpc → subnet → service (never deeper).
- Never nest containers of the same tier (e.g. subnet inside subnet, vpc inside vpc).
- Prefer flatter hierarchy — combine AZ/group boxes only when essential.

━━━ SECTION 5 · EDGE RULES ━━━
5.1 Primary path (solid, left → right, consecutive steps)
One solid edge per step transition. Main band only.

5.2 Secondary (dashed)
Async, events, pub/sub, replication, logging. Route conceptually below VPC band.
Exactly ONE compute → monitoring edge per diagram.

5.3 Topology constraints
| Rule | Detail |
|------|--------|
| No mesh | ≤2 solid edges out per non-LB node |
| No skip | No A→C if A→B→C exists |
| No backflow | Source left of target on main path |
| No bidirectional | Never A→B and B→A |
| No sibling edges | Same subnet = no edge |
| No duplicates | One edge per ordered pair |

5.4 Edge label rules (critical — prevents overlap)
- Allowed: `HTTPS` `SQL` `Redis` `REST` `gRPC` `TCP` or `null`
- Forbidden: `SQL HTTPS` `Redis HTTPS` `HTTP/S` `Logs/Metrics` `Get Secrets` or any two-word label
- Default to `null` — the layout engine and icons convey meaning
- At most one labeled edge among edges sharing the same source node

5.5 Edge routing (layout engine — design topology to help it)
- Sequential flow reduces crossing edges
- Fan-out through LB/API/queue, not raw mesh from compute
- Place targets that receive many edges in distinct zones (not stacked vertically on main row)
