## Architecture Principles (apply to every diagram)

### 1. Security (highest priority)
- Every network boundary needs protection: WAF at edge, security groups at compute, encryption at rest in databases.
- Secrets and keys in dedicated services (Secrets Manager / KMS / Key Vault), not in environment variables or code.
- IAM with least privilege: separate service roles for compute, database, and messaging components.
- Network isolation: public subnets only for load balancers and gateways; compute and data in private subnets.
- Encryption in transit everywhere (TLS); encryption at rest for all storage.

### 2. Reliability
- Eliminate single points of failure: multi-AZ for compute, managed DB with auto-failover, redundant load balancers.
- Auto-scaling for stateless compute tiers; health checks on every load balancer target.
- Async decoupling via queues/event buses between services that can tolerate latency.
- Use managed services (RDS, ElastiCache, Cloud SQL) over self-managed for built-in HA.

### 3. Performance Efficiency
- Match compute to workload: serverless for variable/spiky, containers for steady, VMs only for specialized needs.
- Cache aggressively: CDN for static assets, Redis/Memorystore for session and app data.
- Read replicas for read-heavy databases; partition hot data from cold/archival.
- Choose regional services over zonal for higher durability and simpler DR.

### 4. Cost Optimization
- Right-size compute: do not provision EC2/GCE when Lambda/Cloud Run suffices for the workload.
- Avoid idle resources: auto-scaling to zero where possible, NAT gateways only if private subnets need outbound internet.
- Use managed services over self-hosted (RDS beats EC2 MySQL for all but edge cases).
- Include cost-aware suggestions in every diagram.

### 5. Operational Excellence
- Every diagram needs observability: centralized logging, metrics dashboard, structured alerting.
- Infrastructure as Code: all resources should be deployable via Terraform, CDK, or Pulumi.
- Document runbooks via flow_steps: what happens at each step guides operations and incident response.
- Include CI/CD pipeline components when deployment automation is relevant.

## Pattern Selection Guide
| Pattern | Best For | Avoid If |
|---------|----------|----------|
| 3-Tier Web | Traditional CRUD apps, monoliths, relational DB required | Event-heavy workloads, very high scale per service |
| Microservices (K8s) | Independent deployability, polyglot services, high scale | Small team, simple CRUD, steep K8s learning curve |
| Event-Driven | Async processing, data pipelines, decoupled services | Simple request-response flows, low latency requirements |
| Serverless | Variable/spiky workloads, simple APIs, event handlers | Long-running compute, stateful workloads, cold-start sensitive |
| Static Site + CDN | Marketing sites, docs, SPAs, low-cost global content | Dynamic/server-rendered applications |

## Anti-Patterns (never include these in a diagram)
- Database in public subnet with public endpoint → always private subnet
- Single instance without HA → eliminate this single point of failure
- Everything in one flat subnet → no network segmentation
- No monitoring or logging → blind operations
- Synchronous coupling between microservices → defeats loose coupling
- No IAM roles or access controls → security violation
- Compute node with 4+ outgoing solid edges → insert queue, API gateway, or service mesh
