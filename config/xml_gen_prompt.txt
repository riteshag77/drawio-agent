## Canonical Container Hierarchy (provider-agnostic)

Every diagram follows this abstract container tree. Each provider uses its own labels, but the structural role is identical.

```
[Cloud Provider Boundary]           (AWS Cloud | Azure | Google Cloud)
 └─ [Region]                        (us-east-1 | East US | us-central1)
     └─ [Virtual Network]           (VPC | VNet | VPC)
         ├─ [Cross-Zone Load Balancer / Gateway]   (network-level, sibling of Zone containers)
         ├─ [Zone]                                 (one per AZ/Availability Set; repeat per zone)
         │   ├─ [Public Subnet]                    → internet-facing infra only
         │   ├─ [Private App Subnet]               → compute / application-tier services
         │   └─ [Private Data Subnet]              → data-tier services
         ├─ [Security/Identity Group]              → identity, encryption, secrets (zone-spanning)
         ├─ [Monitoring/Observability Group]       → logging, metrics, audit (zone-spanning)
         └─ [Management/Ops Group]                → automation, backup, patching (zone-spanning)
 └─ [Edge/Global Layer]             — NOT inside Region/Network; sits at provider perimeter
     Internet → Client → DNS → CDN → WAF → [Load Balancer]
     Static assets served by CDN (e.g. S3/Blob/Cloud Storage)
```

Rules:
- For every cloud platform present in the diagram, instantiate one copy of this tree
- Use the existing container ids/labels from the diagram — never invent generic names
- If a container level doesn't exist in the diagram (e.g., no Region group), place its children at the next existing parent level

- Keep labels SHORT (1-2 words max). Add labelBackgroundColor=#F5F5F5;fontSize=11; for labeled edges
- For edges WITHOUT labels: omit value entirely
- Cross-container edges: set the edge's parent="1"

Edge types:
- Solid (strokeWidth=2): primary data flow
- Dashed (strokeWidth=2;dashed=1;): optional/async

## Multi-Cloud Rules

If the diagram contains more than one provider boundary (e.g., AWS Cloud and Azure side by side):

1. A service's parent chain must stay entirely inside its own provider's boundary. Never nest an AWS service under an Azure or GCP container, or vice versa.
2. Cross-provider communication must be an edge between nodes — never containment.
3. If the user doesn't specify which provider a new service belongs to, infer it from the service name/type (e.g., "Cosmos DB" → Azure) rather than defaulting to the first or largest boundary.

## Multi-Zone Duplication

If the Virtual Network has N zones and a new service is app-tier or data-tier (categories 5-6), mirror it into every zone's corresponding subnet (App → App, Data → Data) at the same relative role. Match the existing naming convention (e.g., secondary-zone database node named as replica if primary is named as primary). Do not mirror edge/global, security, monitoring, or management services — those are zone-spanning by design.
