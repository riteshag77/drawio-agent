## Canonical Phase Hierarchy — STRICT NESTING (CRITICAL)

Every phase is a top-level container (`parent="1"`); every producer/consumer/store leaf sits
**inside** its phase via `parent="<phase-id>"`. Phases sit side by side, ordered left → right
by data journey order:

```
[phase_ingest]   [phase_process]   [phase_store]
   ↑ enters          ↑ transforms      ↑ persisted
                                           ↓          ↘
                                     [phase_consume]  [phase_saas]
                                        ↑ read           ↑ SaaS producers/
                                        downstream —     consumers — own
                                        below Store,     vertical shelf,
                                        same column       below Store too

 (ingest/process/store are siblings, each parent="1"; phase_consume AND
  phase_saas are also parent="1" but both excluded from the L→R rank — the
  engine anchors both under phase_store, stacked one above the other, since
  Consume reads FROM Store and SaaS products commonly exchange data with
  Store too; leaves inside each are parent=<phase-id>)

[phase_control]  ← optional dashed shelf, BELOW the data-plane row, parent="1"
   ↑ schema registry / catalog / schedules — never IdP/WAF
```

Only these ids are ever `parent="1"` containers (plus optional external actors and the
overview/legend). **Every** producer/consumer/store/broker/SaaS leaf must be nested inside
one of the phases via `parent=` — never a floating leaf on `parent="1"`.

**Required id prefix (CRITICAL — the diagram is laid out by a deterministic engine that finds
phases by this exact id, not by label):**
- `phase_ingest`, `phase_process`, `phase_store`, `phase_consume` — emit **exactly** these
  ids for whichever phases apply (omit a phase entirely if nothing belongs in it; never
  emit an empty phase shell).
- `phase_saas` (REQUIRED when any enterprise SaaS producer/consumer is in inventory) — a
  **dedicated** shelf for SaaS products, distinct from the cloud-native phases. **Do not**
  place a SaaS leaf inside `phase_ingest`/`phase_process`/`phase_store` — it always goes in
  `phase_saas` instead.
- `phase_control` (optional) for the control-plane shelf when schema registry / catalog /
  schedules are in inventory.
- A leaf's `parent` MUST be the phase id it logically belongs to.

**Parent chain examples:**
- `phase_ingest` → parent `"1"`
- `api_gw_1` → parent `phase_ingest`
- `phase_process` → parent `"1"` (sibling of `phase_ingest`, not nested inside it)
- `lambda_1` → parent `phase_process`
- `phase_store` → parent `"1"`
- `db_1` → parent `phase_store`
- `replica_1` → parent `phase_store`
- `phase_consume` → parent `"1"`
- `dashboard_1` → parent `phase_consume`
- `phase_saas` → parent `"1"`
- `salesforce_1` → parent `phase_saas`
- `phase_control` → parent `"1"`
- `schema_registry_1` → parent `phase_control`

**You do not need to compute final pixel geometry.** A deterministic layout engine
(rank-and-order layered layout) recomputes every phase's x/y/width/height and grids every
leaf inside its phase after this call — your job is correct **grouping** (right leaf → right
phase via `parent=`) and correct, labeled **edges**; emit reasonable placeholder geometry
(e.g. phases roughly 260×200, leaves 78×78) but do not spend effort perfecting alignment,
since it will be discarded and rebuilt. `phase_consume`'s and `phase_saas`'s anchor
positions (both under `phase_store`) are also finalized by the engine — focus on getting the
right leaves into each, not their coordinates.

### Layout gaps (for placeholder geometry only — engine will finalize)
- Horizontal gap between phase columns: **80–120px**
- Phase top edges align (same y) — a shared data-plane band, not a staircase
- `phase_consume` and `phase_saas` sit **below** `phase_store` (same column), stacked with a
  clear vertical gap (≥70px) between each
- `phase_control` sits **below** the data-plane row with a clear vertical gap (≥70px)
- Container padding: **20–28px** sides/bottom, **≥48px** top for the phase title band
- Leaf grid inside a phase: same CORE pitch rules (max 4/row, 180–220px pitch) — except
  `phase_saas`, which stacks its leaves **vertically** (one column), mirroring Logical's
  `domain_saas` shelf.

### Canvas (clean)
- **Data plane** corridor **left → right**: `phase_ingest` → `phase_process` → `phase_store`, with `phase_consume` and `phase_saas` both anchored directly below `phase_store` (Consume reads *from* Store; SaaS is its own shelf, not a 4th peer column and not mixed into the cloud-native phases).
- **Control plane** optional dashed shelf (`phase_control`: schema registry, schedules, Glue catalog) when in inventory — never IdP/WAF.
- SaaS producers/consumers go in `phase_saas`, vertically stacked, ordered top-to-bottom by journey role. Never parent leaves under `overview_panel`.
- **No** `note_*` / `ctrl_*` prose cards. Journey → Overview + `step_markers` badges on major hops.
- Legend when needed: sync/async and `[PII]` / `[Non-PII]` / `[PCI]`.

### REQUIRED resilience companions (when app calls external SaaS AND a primary store exists)
These are **SaaS+store companions**, not density padding. Thin inventory without SaaS stays sparse.

1. **Dead-letter / retry** in `phase_process`: Amazon SQS (or generic DLQ) leaf. Edge from app/portal → DLQ, dashed, label `JSON: Failed API Retries`.
2. **Backup / retention** in `phase_store`: S3 (or object archive) leaf. Edge from primary DB → archive: `Automated Snapshots / Archive`.
3. **CDC / read replica**: secondary store leaf labeled e.g. `Aurora (Read Replica)` (or platform equivalent), inside `phase_store`. Edge primary → replica: `CDC / Replication`.
4. **Schema registry** on the `phase_control` shelf: AWS Glue / Schema Registry. Edge from app → registry: `Validates Payload Schema`.

### ALLOWED nodes
Producers/consumers, named stores/brokers/ETL/cache/replicas from inventory, control-plane orchestration when present, plus the REQUIRED companions above when SaaS+store apply. Keep cloud `shape_type`.
Enterprise SaaS producers/consumers (Salesforce, Workday, Guidewire, Stripe, …): use `shape_type=saas_<vendor>` when present — place in `phase_saas`, **never** in `phase_ingest`/`phase_process`/`phase_store`/`phase_control`.

### ALLOWED edges (every edge labeled)
`JSON:…`, `SQL:…`, `Event:…`, `Cache:…`, `Object:…`, `CDC:…`, `Batch:…` — add `[PII]` / `[Non-PII]` / `[PCI]` when request implies sensitivity (never invent PII). Keep each label **≤ 28 characters** when possible (short type + optional tag).
Retry/DLQ edges: dashed=1.

### Arrow / line craft (CRITICAL — readability)
- One primary data corridor L→R (ingest → process → store), with the store → consume hop dropping down to the anchored Consume phase. Secondary/async dashed and sparse.
- Orthogonal edges; exit/entry from relative placement — never all at mid-face.
- Every labeled edge **must** include `labelBackgroundColor=#F5F5F5;fontSize=11;fontColor=#333333` so payload text is readable.
- Park labels in the clear band between phases — **never** on top of store/broker icons.
- Parallel hops: offset or face-spread; wrap density rather than crossing labels through icons.

### FORBIDDEN
UI wireframes, WAF/Shield/auth login sequences, VPC/AZ wallpaper, security-control essays, capability org charts, note/ctrl cards, phase containers nested inside each other, any leaf on `parent="1"` that isn't an external actor or SaaS peer.
Do **not** invent brokers when SaaS+store are absent.

### Density
