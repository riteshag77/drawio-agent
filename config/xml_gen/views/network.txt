## Network / deployment view (this pack only)

Use this pack **with** the shared CORE craft. This page answers: where do things run, how is the network nested, and what is the request path through Cloud → Region → VPC → Zone → Subnet.

## Canonical Container Hierarchy — STRICT NESTING (CRITICAL)

Every internal box must be **visually and structurally wrapped** inside its outer layer. Nesting is done with `parent="<outer-id>"` and **relative** child geometry — never by drawing boxes side-by-side on the root canvas that only look nested.

```
[Cloud Provider Boundary]              ← OUTER WRAPPER (only this + background + optional Users sit on parent="1")
 ├─ [Region]                           ← parent = Cloud id
 │   └─ [Virtual Network] (VPC|VNet)   ← parent = Region id
 │       ├─ [Load Balancer / Gateway]  ← parent = VPC id (sibling of Zones)
 │       ├─ [Zone] × N                 ← parent = VPC id
 │       │   ├─ [Public Subnet]        ← parent = Zone id
 │       │   ├─ [Private App Subnet]   ← parent = Zone id
 │       │   └─ [Private Data Subnet]  ← parent = Zone id
 │       │       └─ [service icons]    ← parent = Subnet id
 │       ├─ [Security Group]           ← parent = VPC id  (NO edges)
 │       ├─ [Monitoring Group]         ← parent = VPC id  (NO edges)
 │       ├─ [Integration Group]        ← parent = VPC id  (NO edges)
 │       └─ [Management Group]         ← parent = VPC id  (NO edges)
 └─ [Edge/Global Layer]                ← parent = Cloud id (sibling of Region, still INSIDE Cloud)
     └─ DNS / CDN / WAF / static       ← parent = Edge layer id
```

**Outer-layer wrap rules:**
1. Create the Cloud boundary first. Its `parent="1"`. Size it large enough to contain Region + Edge + padding.
2. Region is **inside** Cloud (`parent=<cloud-id>`). VPC is **inside** Region. Zones/subnets/groups are **inside** VPC. Services are **inside** their subnet or supporting group.
3. **FORBIDDEN:** Region, VPC, Zone, Subnet, Security/Monitoring/Integration/Management, or Edge as `parent="1"` siblings floating beside the Cloud box, including via absolute canvas coordinates that only make a box *look* nested. Overlap ≠ containment — if it belongs in the hierarchy, it must be a real child (via `parent=`) of the layer above it.
4. Outer containers must be **larger than** the bounding box of all their children. Use **tight** shrink-wrap: pad **20–28px** sides/bottom, **≥48px** top for title — no huge empty regions. Grow Cloud/Region/VPC/Zone/Subnet until every child fits; do not leave oversized empty boxes.
5. Optional **Users / Internet / Client** icons: if used, they are **always** `parent="1"` (left of Cloud) — external actors represent people/systems outside the cloud boundary, not a service to be classified or nested. Everything else cloud-related stays wrapped inside Cloud.
6. **FORBIDDEN:** an external-actor icon (Users / Internet / Client / mobile / on-prem / IoT device) as a child of Cloud, Region, VPC, or any other container. It never has a classification decision — it is not a service.
7. **Cross-VPC/cross-account connectivity hubs** (Transit Gateway, VPN Gateway, Direct Connect, PrivateLink and equivalents) connect *multiple* VPCs/accounts/regions — **never** place one as an ordinary sibling icon inside a single VPC's service row (that stretches the pitch to reach the other VPC and balloons every ancestor's width). Place it at the Cloud level instead, alongside the Edge/Global Layer, and connect it to each VPC with an edge, never shared containment.

**Parent chain examples (AWS):**
- `aws_cloud` → parent `"1"`
- `region` → parent `aws_cloud`
- `vpc` → parent `region`
- `az1` → parent `vpc`
- `subnet_app_1` → parent `az1`
- `lambda_1` → parent `subnet_app_1`
- `security_group` → parent `vpc`
- `edge_layer` → parent `aws_cloud`

## Network layout gaps (CRITICAL)

- Vertical gap between subnet tiers (Public → App → Data): **100–140px**
- **Gap below Zones (CRITICAL):** supporting groups (Security / Monitoring / Integration / Management) must sit **strictly below** all Availability Zones — minimum **70–80px** clear space from the **lowest Zone bottom** to the **top** of those groups. Never overlap Zones or Subnets.
- **Gap between Subnets and supporting groups:** same rule — no shared y-range with any Zone/Subnet box; leave a modest empty band between the subnet tier and the four groups
- Horizontal gap between the four supporting groups side by side: **20–30px** (do not let them touch or overlap)
- Horizontal gap between peer AZ containers: **20–30px** (do **not** use icon pitch between AZs)

Inside every **Public / Private App / Private Data subnet** and every **Security / Monitoring / Integration / Management** group, apply CORE's service grid (max 4/row, pitch rules).

## Network Artist Principles (additions)

1. One primary story: Client → Edge → LB/API → App → Data. Secondary paths are dashed and sparse.
2. Nest only real boundaries (Cloud → Region → VPC → Zone → Subnet).
3. Inventory ≠ flow — Security / Monitoring / Integration / Management are icon shelves with **zero** edges.
4. Align ruthlessly — peer AZs share top/height; subnet rows align across AZs.

## Cross-Cutting Groups — NO EDGES (CRITICAL)

Place **four** separate groups side by side below the Zones, inside the VPC (`parent=<vpc-id>`). Do not merge them.

| Group | Example services |
|-------|------------------|
| Security | IAM, KMS, Secrets Manager, Cognito, ACM, GuardDuty, WAF (if not on edge), Shield, Inspector |
| Monitoring | CloudWatch, CloudTrail, Config, X-Ray, logging/metrics products |
| Integration | SQS, SNS, EventBridge, Step Functions, Service Bus, Pub/Sub (when used as bus) |
| Management | Systems Manager, Backup, Automation, Ops tools |

**ABSOLUTE RULE — NO LINES:**
- Do **NOT** create any edge (`edge="1"`) with source or target equal to a cell inside Security, Monitoring, Integration, or Management groups
- Do **NOT** draw edges to/from the group containers themselves
- These services are shown for architecture completeness only — they are never on the request/data path in the diagram
- Primary flow edges only connect: Edge/Client → LB/API → App tier → Data tier (and optional CDN/DNS/WAF on the edge path)

## Network edge labels

- Edge labels: **omit by default**. If used → 1–2 words only AND include `labelBackgroundColor=#F5F5F5;fontSize=11;fontColor=#333333` (e.g. HTTPS, async, read)

## Network edge cases (brief)

- 5–8 services in one App subnet → wrap to 2 rows; grow subnet/Zone height; keep pitch
- 2–3 AZs mirrored → same relative roles and y-rows across AZs; do **not** mirror Security/Monitoring/Integration/Management/Edge
- LB / API Gateway → sibling of Zones inside VPC (not inside a subnet)
- Public subnet with only NAT/Bastion → still use title band + padding; do not invent empty stretch unless aligning AZ columns
- Empty tier → omit the empty subnet rather than a huge empty box
- Multi-cloud → each provider keeps its own tree; cross-cloud = edge only, never nesting
- Users / Internet → outside Cloud on left (`parent="1"`); edge into Edge layer or LB

## Anti-Patterns — FORBIDDEN (Network)

1. Edges into Security / Monitoring / Integration / Management
2. Region/VPC/Zone/Subnet as `parent="1"` siblings that only look nested
3. Mirroring Security / Monitoring / Integration / Management / Edge into every Zone

## Output Rules — Parent (Network)

- Every cell (except background, optional Users/Internet, and edges) must sit on the hierarchy chain above — **wrapped inside** its outer layer via `parent`
- Leaf `parent` = classification container id — never `"1"` for VPC/Zone/Subnet/supporting groups/services
- Only Cloud (outer wrapper), page background, and optional external Users/Internet use `parent="1"`
- Child geometry is **relative to parent** (x/y origin = parent's top-left), never absolute canvas coords for nested cells
- Never infer parent from coordinate overlap — if a box is inside another visually, its `parent` MUST be that outer box's id

## Multi-Zone

Mirror app-tier and data-tier into every Zone's matching subnet. Do **not** mirror Security / Monitoring / Integration / Management / Edge services.
