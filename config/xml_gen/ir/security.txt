# Security / trust architecture view — judgment content

Page name: **Security**. Role: Principal Security/Trust Architect (25+ years,
enterprise estate) briefing risk owners on protections and trust boundaries —
including third-party/partner risk, not just the consumer perimeter. 60-second
trust briefing: public surface → perimeter → identity → partner/B2B → private
→ restricted → detect / external SaaS. Microservice soup or VPC wallpaper → fail.

## Corridor vocabulary (fixed ids)

Main row, ordered left→right by trust level — use whichever apply, omit the
rest: `zone_public`, `zone_dmz`, `zone_identity`, `zone_partner`,
`zone_private`, `zone_restricted`, `zone_detect`.

Anchored shelf: `zone_external_saas` — anchored under `zone_restricted`
(SaaS vendors typically process/receive the organisation's sensitive data).
`zone_external_saas` is the **only** id allowed in `anchored`. Every other
zone — including `zone_detect` — is a main-row corridor, never a shelf.

## `zone_partner` vs `zone_external_saas` — do not conflate

- `zone_external_saas` = SaaS products **the organisation subscribes to and
  consumes** (Salesforce, Workday, Guidewire, Okta-as-IdP) — the org is the
  customer.
- `zone_partner` = **other organisations** integrating over B2B (brokers,
  agencies, resellers, distributors, suppliers, reinsurers, marketplace
  counterparties) — contractual, often mutual-auth (mTLS/API keys), with its
  own federation trust distinct from the org's workforce IdP.

## Leaf vocabulary

Keep cloud `shape_type` (`aws_*`/`gcp_*`/`azure_*`) on inventory services:
IdP/IAM, WAF/API GW/public ALB/Shield, KMS/secrets/ACM, bastion/private
access, private app, sensitive-data boundary, detect tools.

**Collapse density:** one `zone_private` for apps (not one zone per
microservice) and one `zone_restricted` sensitive-data boundary (not every
table/service as its own zone). Extra peer services stay as leaves inside
those zones.

External IdP/enterprise SaaS (Okta, Salesforce, Workday, Guidewire, …):
`shape_type=saas_<vendor>` — place in `zone_external_saas`, `zone_public`, or
`zone_identity` as a trust peer, **never** as a private-app child.

Business partners (brokers, agencies, resellers, distributors, suppliers,
reinsurers, marketplace counterparties): use `shape_type=security_partner_org`
(a curated double-border tile — not a cloud `shape_type`) plus a dedicated
**Partner API Gateway** leaf, all inside `zone_partner` — **never** as
private-app children, **never** merged into `zone_external_saas`.

## Required companions

**When a private app + enterprise SaaS both appear:**
1. Secrets Manager (or Key Vault) leaf inside `zone_private`. Flow app →
   secrets, labeled `Fetches Credentials (TLS)`.
2. `zone_detect` with GuardDuty (or equivalent) + CloudWatch/Monitor. Dashed
   flow private app → detect, labeled `Logs & Telemetry`.

**When business partners are in inventory:**
1. Partner API Gateway inside `zone_partner` — the single ingress/egress
   point for partner traffic, distinct from the consumer WAF/ALB.
2. Flow partner leaf → gateway, labeled `Partner API (mTLS)`.
3. Flow gateway → `zone_identity` (federation broker), labeled
   `B2B Federation` — partners authenticate via their own federated identity,
   not the workforce IdP.
4. Flow gateway → the **specific** private-zone service it's scoped to
   (never the whole zone by implication), labeled `Scoped Partner API`.

## Allowed edges

`AuthN`, `AuthZ`, `TLS`, `mTLS`, `inspect`, `perimeter cross`, `private path`,
`issues token`, `Fetches Credentials (TLS)`, `Logs & Telemetry` (dashed),
`Partner API (mTLS)`, `B2B Federation`, `Scoped Partner API`.

Set each flow's structured `protection` to match its label: `mtls` for any
`(mTLS)`-labeled flow (partner/gateway links), `tls` for `(TLS)`-labeled
flows, `none` for anything genuinely unencrypted (e.g. internal telemetry
over a private path with no TLS termination noted). Any flow that crosses
into `zone_public` or `zone_partner` should carry `protection` — a boundary
crossing with `protection: none` is flagged for review.

### Mini example

```json
"external_actors": [{"id": "users", "kind": "users", "label": "Users"}],
"corridors": [
  {"id": "zone_public", "label": "Public", "leaves": [
    {"id": "api_gw", "shape_type": "aws_api_gateway", "label": "API Gateway"}
  ]},
  {"id": "zone_identity", "label": "Identity", "leaves": [
    {"id": "cognito", "shape_type": "aws_cognito", "label": "Cognito"}
  ]},
  {"id": "zone_private", "label": "Private", "leaves": [
    {"id": "item_api", "shape_type": "aws_ecs", "label": "Item API"}
  ]},
  {"id": "zone_detect", "label": "Detect", "leaves": [
    {"id": "guardduty", "shape_type": "aws_guardduty", "label": "GuardDuty"}
  ]}
],
"anchored": [],
"flows": [
  {"source": "users", "target": "api_gw", "label": "TLS", "protection": "tls"},
  {"source": "api_gw", "target": "cognito", "label": "AuthN"},
  {"source": "api_gw", "target": "item_api", "label": "private path"},
  {"source": "item_api", "target": "guardduty", "label": "Logs & Telemetry", "primary": false}
]
```

`zone_detect` is always a **main-row** corridor — never put it in `anchored`
(only `zone_external_saas` may be anchored).

**Forbidden:** Orders/Catalog/Checkout/UI soup, Kafka-as-hero, DB
table/CRUD labels, full AZ/subnet wallpaper (that's Network's lens), SaaS
leaves inside `zone_private`, partner leaves inside `zone_private` or
`zone_external_saas`, routing partner traffic **straight into** `zone_private`
without passing through `zone_partner`'s Partner API Gateway, putting any leaf
in `external_actors` that is not actually outside the trust boundary.

## Density

8–12 when supported; 5–7 when thin — never invent fake controls except the
required companions above when their trigger conditions are met.
