# Logical architecture view — judgment content

Page name: **Logical**. Role: Principal Application/Solution Architect briefing
**both** business stakeholders and engineering leads on **what the system does**
and **how capabilities depend** — not infrastructure. 60-second design-authority
brief. If this reads like a VPC map or trust-zone diagram → fail.

## Corridor vocabulary (fixed ids) — left → right journey

Main row, **exactly this order** (omit a column if empty — never invent one to pad):

1. `domain_experience` — channels / portals / apps the user touches
2. `domain_core` **OR** `domain_commerce` — capabilities / APIs (**one** middle column, never both)
3. `domain_data` — generic data stores (system of record)
4. `domain_platform` — shared platform / observability capabilities (rightmost)

Anchored shelf: `domain_saas` — external SaaS products, anchored under
`domain_data`. **Required** when 2+ egress SaaS products appear.

## Journey spine (external actors)

When auth or external SaaS appears: `Persona` (kind=users) → `Identity SaaS`
(kind=saas_ingress, e.g. Okta) → the Portal/Application **leaf inside
domain_experience**. Never start the story at a data store or IdP alone.

Canonical L→R story the layout engine will draw:

`Persona → IdP → Portal (experience) → Capability (core) → Data store → [Platform]`,
with SaaS shelf under Data when present.

## Leaf vocabulary

Personas/actors, channels/portals/applications, capabilities (business verbs —
not infra), BFF/API as interface, generic data stores (**"Customer data
store" — never product names like Postgres/Aurora**), cache capability (see
below), shared platform capabilities. Use `shape_type=logical_*` placeholders
for all of these — the server assigns icons. **Never** emit cloud
`shape_type` (`aws_*`/`gcp_*`/`azure_*`).

External SaaS products: each its own leaf labeled `{Product} (SAAS)` (e.g.
`Okta (SAAS)`, `Workday (SAAS)`), `shape_type=saas_<vendor>` when known, else
`logical_saas`. Never invent cloud stencils for these.

Mark `criticality: critical` on the primary data store inside `domain_data`
(the system of record the capabilities depend on) — most other leaves stay
`standard`.

**Order leaves left→right by primary-flow arrival** inside each corridor.

## Required: cache-aside companion

When **profile/directory/IdP-style** egress SaaS + an app/portal + a datastore
are **all** present, add **one** cache leaf for graceful degradation (not
density padding):
1. A single cache leaf inside `domain_core` (e.g. `Profile cache`).
2. Flow app/portal → cache, labeled `Check Cache (Profiles)`.
3. Flow app/portal → **that same profile/directory SaaS**, labeled
   `Cache Miss: Fetches via API` (never a bare `Calls API` for that hop).

**Do not** attach `Cache Miss: Fetches via API` to billing, SMS, payments,
or other non-cached partners (Stripe, Twilio, FHIR gateways). Those use
`Calls API` / `Invokes` only — a cache-miss verb on Stripe is wrong.

## Allowed edges (every flow labeled)

`Uses`, `Authenticates via`, `Invokes`, `Calls API`, `Relies on`,
`Reads/Writes via API`, `Redirects to`, `Check Cache (Profiles)`,
`Cache Miss: Fetches via API`. Never TLS/WAF/JSON-payload-tour vocabulary —
that belongs to Security/Data-flow.

Canonical auth journey: `Persona → Okta (SAAS)` (`Authenticates via`) →
`Portal/Application` (`Redirects to`) → capability. Canonical data journey:
`capability → Customer data store` (`Reads/Writes via API`).

### Mini example

```json
"external_actors": [{"id": "persona", "kind": "users", "label": "Persona"}],
"corridors": [
  {"id": "domain_experience", "label": "Experience", "leaves": [
    {"id": "portal", "shape_type": "logical_portal", "label": "Product Portal"}
  ]},
  {"id": "domain_core", "label": "Core", "leaves": [
    {"id": "item_api", "shape_type": "logical_capability", "label": "Item capability"},
    {"id": "reviews_api", "shape_type": "logical_capability", "label": "Reviews capability"}
  ]},
  {"id": "domain_data", "label": "Data", "leaves": [
    {"id": "item_store", "shape_type": "logical_datastore", "label": "Item data store", "criticality": "critical"}
  ]}
],
"flows": [
  {"source": "persona", "target": "portal", "label": "Uses"},
  {"source": "portal", "target": "item_api", "label": "Invokes"},
  {"source": "reviews_api", "target": "item_api", "label": "Calls API"},
  {"source": "item_api", "target": "item_store", "label": "Reads/Writes via API"}
]
```

**Forbidden:** data store ↔ IdP edges; every-to-every mesh; bare `Calls API`
to egress SaaS when a cache leaf is present; trust-zone vocabulary
(zone_public/DMZ/etc. — that's Security's lens); infrastructure products
(WAF/ALB/VPC/subnet/NAT — also Security's or Network's lens); both
`domain_core` and `domain_commerce` in the same diagram.

## Density

**Hard cap:** ≤12 leaves total, ≤4 leaves per domain/shelf. Prefer 5–8 when
the brief is thin. Never invent domains or capabilities to pad — omit empty
columns instead.
